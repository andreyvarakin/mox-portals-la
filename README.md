# Portal Control Center

Панель смотрителя лаборатории нестабильных порталов: список порталов, расчёт риска,
разрешённые действия, журнал событий и сводка по лаборатории. Одностраничное приложение
без бэкенда — состояние живёт в памяти вкладки.

Тестовое задание MOX, вариант «Лаборатория нестабильных порталов».

**Live demo:** будет добавлена после деплоя.

## Сценарий

Оператор следит за межмировыми порталами, оценивает риск и решает, что делать:
стабилизировать портал, закрыть его, отправить наблюдателя или пометить «под вопросом».

Приложение показывает:

- сводку: сколько порталов открыто, сколько критичных, сколько закрыто;
- список «Требуют внимания» в порядке приоритета;
- таблицу всех порталов с параметрами и риском;
- карточку выбранного портала: параметры, риск с объяснением, рекомендацию, действия
  и историю этого портала;
- общий журнал событий по всей лаборатории.

## Стек

React, TypeScript, Vite, Vitest, React Testing Library, ESLint. Зависимостей времени
выполнения, кроме React, нет.

## Запуск

Нужен Node.js `^20.19.0 || >=22.12.0` (требование Vite 8).

```bash
npm install
npm run dev     # дев-сервер на http://localhost:5173/
```

Остальные команды:

```bash
npm run test    # Vitest, однократный прогон
npm run build   # проверка типов (tsc -b) и сборка в dist/
npm run lint    # ESLint
npm run preview # просмотр собранной версии
```

## Архитектура

Три слоя, зависимости направлены только вниз.

**`src/domain`** — предметная модель и чистые функции, без React:

- `portal.ts` — тип `Portal` и статусы;
- `riskEngine.ts` — `calculateRisk`: балл, уровень, факторы, причины;
- `actionEngine.ts` — `getActionAvailability` и `executePortalAction`: что разрешено
  и что меняется;
- `recommendationEngine.ts` — `getPortalRecommendation`: что советуем оператору.

**`src/application`** — состояние приложения:

- `portalAppState.ts` — `PortalAppState`, `createInitialPortalState`, `applyPortalCommand`
  (единственный способ изменить состояние; пишет событие в журнал со снимками «до» и «после»);
- `portalSelectors.ts` — `getPortalSummary`: счётчики и список внимания.

**`src/components`, `src/pages`** — слой представления. Интерфейс вызывает функции domain
и application и **не содержит своих бизнес-правил**: доступность кнопок, риск, рекомендации
и сводка приходят из перечисленных выше функций.

**`src/data`** — демонстрационный набор порталов (только начальные данные).
**`src/content`** — текст AI Worklog.

Ключевой принцип: риск, рекомендация и сводка **не хранятся** в состоянии — они вычисляются
из текущих данных порталов при каждой отрисовке и поэтому не могут с ними разойтись.
В состоянии лежат только порталы и журнал событий; выбранный портал и незавершённое
подтверждение — это состояние интерфейса.

## Как считается риск

```
балл = 45% × риск низкой стабильности
     + 30% × риск высокой энергии
     + 25% × риск близкого схлопывания
```

Здесь `риск низкой стабильности = 100 − стабильность`, `риск высокой энергии = энергия`,
а риск времени считается на горизонте **120 минут**: чем меньше времени осталось, тем выше
эта часть балла (при 120 минутах и больше она равна нулю).

| Балл | Уровень |
|---|---|
| 0–29 | LOW — низкий |
| 30–59 | MEDIUM — средний |
| 60–79 | HIGH — высокий |
| 80–100 | CRITICAL — критический |

- `creaturesInside` в технический балл риска **не входит** — число существ влияет только
  на допустимость закрытия портала;
- у закрытого портала текущий риск `0 / LOW`: схлопнуться он больше не может;
- то же объяснение доступно пользователю прямо в интерфейсе — в карточке портала,
  свёрнутый блок «Как считается риск».

## Действия и ограничения

| Действие | Что делает | Ограничения |
|---|---|---|
| Стабилизировать | стабильность +25, энергия −10 (в границах 0–100) | нельзя для закрытого портала; отметку «под вопросом» не снимает |
| Отправить наблюдателя | параметры портала не меняет, фиксируется в журнале | нельзя при критическом риске; нельзя в закрытый портал |
| Закрыть портал | статус → «Закрыт», время до схлопывания → «—» | при `creaturesInside > 0` требуется подтверждение; повторно закрыть нельзя; число существ не обнуляется — закрытие не эвакуация |
| Пометить «под вопросом» / снять отметку | ручная отметка оператора | нельзя для закрытого портала; нельзя пометить уже помеченный и снять отметку у непомеченного |

Запрещённое действие — не ошибка: кнопка остаётся видимой, но отключённой, рядом показана
причина запрета, и сама попытка тоже попадает в журнал.

Запрос подтверждения и подтверждённое закрытие — **два отдельных события** журнала: видно
и то, что оператор собирался закрыть портал с существами, и то, что он это подтвердил.

Отметка «под вопросом» — операционный признак, а не уровень риска: такой портал считается
физически открытым и учитывается в счётчике «Открыто».

## Порядок внимания

Список «Требуют внимания» упорядочен по виду проблемы:

```
CRITICAL → HIGH → QUESTIONABLE → MEDIUM
```

Внутри одного вида выше тот, у кого больше балл риска. Портал с низким риском в список
не попадает, **кроме** случая, когда он помечен «под вопросом». Закрытые порталы не попадают
в список никогда.

## Демо-сценарии

Переключатель «Демо-сценарий» есть прямо в интерфейсе, под заголовком страницы. Это обычные
ссылки: переход перезагружает приложение и создаёт новое начальное состояние, поэтому
накопленные события сбрасываются.

| Сценарий | Адрес | Что показывает |
|---|---|---|
| Рабочий набор | `/` | 8 порталов: критические, средний риск, низкий риск, «под вопросом» и уже закрытый |
| Пустая лаборатория | `/?scenario=empty` | настоящее пустое начальное состояние: 0 открытых, 0 критичных, 0 закрытых, пустые список внимания, таблица и журнал |

## Обязательные состояния

| Состояние | Где посмотреть |
|---|---|
| Пустой список порталов | «Пустая лаборатория» (`/?scenario=empty`) |
| Портал с критическим риском | «Врата Бездны» — 88 / 100, уровень критический |
| Запрещённое действие | выбрать «Врата Бездны»: «Отправить наблюдателя» отключено, причина видна |
| Изменение риска после стабилизации | «Врата Бездны»: 88 критический → 73 высокий, критичных 2 → 1 |
| Журнал после нескольких операций | выполнить несколько действий и открыть «Журнал событий» |
| Предупреждение при закрытии с существами | «Пасть Пустоты» — внутри 4 существа |

## AI Worklog

Встроенный AI Worklog находится внизу страницы приложения (якорь `#ai-worklog`) и виден
в обоих демо-сценариях. В нём: инструмент и модель, время разработки, положение дел
с подсчётом токенов, этапы работы с разделением «человек / AI», ключевые запросы, авторские
решения, случаи, где сгенерированный результат потребовал проверки и правки, как всё
проверялось и что стоило бы доработать в реальном продукте.

## Чеклист ручной проверки

Сценарии, проверенные перед сдачей. Каждый выполняется с нуля: после перезагрузки страницы
состояние возвращается к исходному.

1. **Критический портал и стабилизация.** Открыть «Врата Бездны» в таблице → риск 88 / 100,
   уровень критический, три причины риска. Нажать «Стабилизировать» → риск 73 / 100, уровень
   высокий, в сводке «Критичных» 2 → 1, в истории портала появилась запись.
2. **Ограничение для наблюдателя.** На критическом портале «Отправить наблюдателя»
   отключено, причина видна. После стабилизации кнопка активна; отправка добавляет событие
   в журнал, но параметры портала не меняет.
3. **Закрытие с существами.** Открыть «Пасть Пустоты» → «Закрыть портал» → появляется
   предупреждение о 4 существах с выбором «Закрыть всё равно» / «Отмена». Подтвердить →
   статус «Закрыт», существа остаются 4, в журнале **два** события: запрос подтверждения
   и закрытие.
4. **Отметка «под вопросом».** Открыть «Арка Авроры» (низкий риск, в списке внимания её нет)
   → «Пометить как под вопросом» → портал появился в «Требуют внимания» → «Снять отметку» →
   исчез из списка.
5. **Закрытие без существ.** Открыть «Разлом Люмии» (существ 0) → «Закрыть портал»
   закрывает без подтверждения → статус «Закрыт», время до схлопывания «—», портал пропал
   из списка внимания, «Открыто» уменьшилось, «Закрыто» выросло.
6. **Общий журнал.** Выполнить действия над двумя-тремя разными порталами → в «Журнале
   событий» записи идут в порядке действий, у каждой видны время, портал, действие, исход
   и что именно изменилось; счётчик событий совпадает с числом операций.
7. **Пустая лаборатория.** Нажать «Пустая лаборатория» → адрес `?scenario=empty`, сводка
   0 / 0 / 0, «Порталы, требующие внимания, отсутствуют», «Порталов пока нет», «Выберите
   портал», «0 событий», AI Worklog на месте. Вернуться в «Рабочий набор» → снова 8 порталов
   и работающие действия.

Дополнительно проверялись ширины 1440, 1024, 768, 480 и 360 px (горизонтальной прокрутки
страницы нет, широкая таблица прокручивается внутри своего блока) и консоль браузера —
без ошибок приложения.

## Тесты и проверки

Больше 200 автоматических тестов (`npm run test`):

- модульные тесты domain: риск, правила действий, рекомендации, демо-данные;
- тесты application: применение команд, журнал со снимками, сводка и порядок внимания;
- интеграционные тесты интерфейса на React Testing Library: выбор портала, действия,
  подтверждение закрытия, журнал, демо-сценарии, AI Worklog;
- проверка чувствительности тестов: после этапов логики и интерфейса в код вносились
  подложенные ошибки, каждая должна была уронить хотя бы один тест. Это ручная проверка,
  а не полноценное mutation-тестирование — отдельного фреймворка не использовалось;
- ручная проверка сценариев в браузере на движке Chromium.

## Как шла разработка

Проект собирался небольшими итерациями: доменная модель → расчёт риска → правила действий →
рекомендации → демо-данные → состояние приложения и журнал → сводка → интерфейс только для
чтения → выбор портала и карточка → действия → общий журнал событий → AI Worklog →
демо-сценарий пустой лаборатории. Каждый этап принимался отдельно, после прогона тестов,
сборки, линтера, просмотра diff и ручной проверки в браузере.

## Что было бы иначе в продакшене

- серверное хранение состояния вместо памяти вкладки и сохранение после перезагрузки;
- аутентификация и роли: кто вправе закрывать портал с существами внутри;
- журнал событий на сервере, с фильтрами, поиском и постраничной загрузкой;
- обновления в реальном времени и обратный отсчёт до схлопывания (сейчас время статично);
- согласование формулы риска и порогов с предметными специалистами и вынос их в настройки;
- проверка входных данных на границе системы, отчёт об ошибках и мониторинг.

Для тестового задания намеренно выбран меньший, но законченный объём: понятная логика,
аккуратные состояния и проверяемый результат вместо широкого набора незавершённых функций.
